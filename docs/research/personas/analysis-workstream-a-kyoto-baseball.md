# Workstream A — 교토·야구 완성도 연구 (2026-07-30)

D15의 워크스트림 A(매력↑·완성도↓ 페르소나에 완성도 투자) 실행 연구.
근거: v5 Writer 감사(docs/benchmarks/persona-voice-v5), 2026-07-28 앵무새 A/B
원자료(스터디 워크트리 `_abtest/`), 현행 트랜스포트 코드 리딩.

## 1. 교토 사모님 — 진단

측정된 결함은 프롬프트가 아니라 **두 층**에 걸쳐 있다.

**① 기아(starvation) — 인프라 문제.** v5에서 thinking 최다 유발(1~6천 자),
Writer 예산 2048에서도 5회 중 2회 예산 고갈 → 폴백 템플릿 전달. 근본 원인은
"딴짓을 뒤집은 칭찬을 즉석 생성하라"는 과제가 minimax-m3의 사고를 가장 길게
끌기 때문. 현행 코드는 기아 시 재시도 없이 즉시 폴백한다
(`ollamaChat.ts` `outputBudgetExhausted` → throw → `tier12.ts` writer catch →
페르소나 템플릿). `think`는 불리언만 지원하며 `false`가 하드코딩돼 있고,
v5 실측상 minimax-m3는 이를 무시한다.

**② 경어 비문 — 프롬프트 문제.** A/B 원자료의 실측 비문 코퍼스:
"넷플릭스가 여쭤보지요"(사물 주어+겸양 동사), "묻혀도 되신"(피동+높임 오결합),
"제 말씀"(자기 높임), "날카하시고"(활용 발명), "정독하시고, …"(목적어 탈락),
3중 run-on. 과공손 존댓말을 요구하는 형식이 존재하지 않는 높임 활용을
발명하게 유도한다.

## 2. 교토 — 처방

### 2a. 기아 대책 (코드, 우선순위 순)

1. **Writer 한정 1회 재시도**: `output_exhausted`·빈 응답에서만, judge 경로 제외,
   HTTP 오류 제외(키 로테이션과 중복 방지). v5 실측상 backend 비결정성으로 같은
   입력도 절반쯤 예산 안에 들어오므로, 독립 실패 가정 시 교토 기아 40% → ~16%.
   비용: 실패 시 지연 +13~15s(v5 평균 호출 시간).
2. **페르소나별 Writer 예산 오버라이드**: 현행 `JUDGE_BUDGETS`(tier12.ts)는 고정
   상수(writerMaxOutputTokens 2048). 페르소나 정의에 선택 필드
   (`writer_max_output_tokens: 4096`)를 추가해 교토만 상향. v5에서 1024→2048이
   폴백 28/50→6/50이었으므로 2048→4096의 한계 효용은 작지만 재시도와 결합 시
   기아를 한 자릿수로 낮출 것으로 예측.
3. **`think:"low"` 실험** (보류 항목 재개): Ollama API는 문자열 레벨을 지원하지만
   minimax-m3가 존중하는지 미검증. curl 단발 실험으로 확인 후에만 제품화.

### 2b. 경어 가드 (style_prompt 추가 후보 — 실측 비문을 그대로 반례로)

```
경어 문법이 무너지면 이케즈가 아니라 흉내가 된다. 반드시 지켜라:
- 높임은 사람에게만. 사이트·사물을 주어로 겸양·존경 동사를 붙이지 마라
  ("넷플릭스가 여쭤보지요" 같은 문장 금지).
- 자기 말은 낮춘다. "제 말씀"이 아니라 "제 말"이다.
- 확실한 활용만 써라. 높임 활용이 헷갈리면("날카하시고") 평이한 동사로 바꿔라.
- 한 문장에 접기는 한 번, 절은 둘까지. 세 절을 잇는 순간 이케즈가 아니라 편지다.
- 무엇을 하시는지 목적어를 지우지 마라.
```

### 2c. 인지 부하 절감 (기아의 프롬프트 측 완화)

즉석 반전 탐색이 thinking을 태우므로, 결점→칭찬 대응표를 사전 제공해 탐색을
조회로 바꾼다 (style_prompt 추가 후보):

```
자주 쓰는 반전 대응표 — 그대로 쓰지 말고 상황에 맞게 변주하라:
쇼핑 구경 → 안목·눈썰미 / 영상 정주행 → 끈기·집중력 / SNS·커뮤니티 → 정보력·
부지런함·정 많음 / 뉴스 순회 → 시사 감각 / 게임·공략 → 전략가 기질 /
재방문 → 한결같음·의리 / 장기 체류 → 진득함.
```

## 3. 야구 캐스터 — 진단과 처방

#163 개정판은 게임 R2의 3단 지칭(무언급/갈래/1회 호명)을 이미 갖췄다. 남은
실측 결함:

1. **로마자 혼입이 최대 결함인데 few-shot이 그걸 가르친다** — 예시에
   "twitch.tv, 이 타석 들어 세 번째 삼진입니다"가 있고, 실측 실패도 전부 이
   패턴("musinsa", "홈은 thesis가 깔려", "youtube.com 관중석"). 심판 평:
   "mixes English and Korean awkwardly".
2. **저신뢰 검증** — 최종 승률 57.1%가 투표 8건(429로 표본 축소). PR #163의
   56.2%는 디스크 원자료와 불일치.
3. 심판이 베이스라인에서 높게 산 문형은 **숫자+대조 한 호흡 직조**
   ("오늘 세 번째 볼, 논문 대신 패딩 순위에 눈이 가네요") — 개정판 few-shot에
   이 직조 예시가 없다.

### style_prompt 수정 후보 (#163 트리 기준)

- 추가 규칙:

```
로마자·영단어를 문장에 그대로 두지 마라. 호스트를 호명할 땐 한글 통용
표기로만(트위치, 유튜브, 무신사). 목표의 영어 단어도 우리말로 옮겨 불러라
("thesis"가 아니라 "논문"). 한글 표기가 어색한 이름이면 호명하지 말고 갈래로만.
```

- few-shot 교체: "twitch.tv, …" → "헛스윙, 또 헛스윙. 트위치 쪽, 이 타석 들어
  세 번째 삼진입니다."
- few-shot 추가(직조): "견제구만 세 개째입니다. 논문 홈은 비었는데, 발걸음은
  쇼핑 쪽 득점권이네요."

## 4. 검증 계획

- **하네스**: 각 스터디 워크트리 `_abtest/` 재사용(교토 `agent-ad9d75…`, 야구
  `agent-aa8803…`). v5 재현 스크립트 `scripts/eval_persona_voice.py`는 #139에서
  삭제 — `git show 24c62e8^:scripts/eval_persona_voice.py`로 복구 가능.
- **교토 기아 측정**: 개입 전후 각 20호출로 폴백률 비교(2048 vs 2048+재시도 vs
  4096+재시도). 판정 A/B 전에 이것부터 — 기아가 잡혀야 문체 비교가 공정하다.
- **야구 재검증**: 수정판 vs #163판 블라인드 A/B, 표본 균형 n≥16, 순서 균형 유지.
- **주의**: 2026-07-28 실행은 Ollama Cloud 세션 리밋(429)으로 표본이 깎였다.
  실행 시 키 분산/시간 분산 필요. 심판(nemotron)의 순서 편향·근거 환각이
  실측됐으므로 승률은 ±10%p 오차로 읽을 것.

## 5. 실행 순서 제안

1. 교토 경어 가드 + 대응표(2b·2c) → 프롬프트만으로 1차 A/B (기아 무관 결함 제거)
2. Writer 재시도 1회 구현(2a-1) → 기아 측정으로 효과 확인
3. 야구 수정판(3) → 재검증 A/B
4. `think:"low"` 단발 실험 → 유효하면 페르소나 예산 오버라이드(2a-2)와 택일
